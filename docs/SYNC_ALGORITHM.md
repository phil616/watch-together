# 播放同步算法

本文档描述当前代码实际采用的同步算法。实现分别位于：

- `internal/rooms/state.go`、`internal/rooms/actor.go`：房间权威时间线和房主心跳过滤
- `web/src/player/ClockSynchronizer.ts`：客户端服务器时钟估计
- `web/src/player/DriftCorrector.ts`：有状态漂移控制器
- `web/src/player/SyncController.ts`：播放器事件和缓冲状态机

## 目标与不变量

1. 房主播放器是实际播放进度的物理参考，服务端时间线是所有成员共享的逻辑参考。
2. 房主心跳可以缓慢刷新服务端锚点，但服务端返回的心跳锚点不得反向 seek 房主。
3. 单次高延迟、时钟样本跳变、`waiting` 或 `canplay` 事件不得触发 hard seek 或全房间缓冲。
4. 播放、暂停、拖动、倍速和确认后的房主缓冲仍由服务端 revision 串行排序。
5. 成员缓冲只暂停该成员的校准，不拖停整个房间；只有房主持续缓冲才协调全房间暂停。

## 权威时间线

播放状态保存锚点位置 `P0`、锚点服务器时间 `T0`、公共倍速 `R`、`timelineEpoch` 和 phase。播放中的期望位置为：

```text
expected(serverNow) = P0 + max(0, serverNow - T0) × R
```

播放和播放中的拖动使用 350ms 的未来锚点，让各客户端有时间收到状态后同时启动。媒体切换或用户主动拖动会递增 `timelineEpoch`；房主心跳只刷新锚点，不改变 epoch。客户端由此能可靠区分“立即定位”和“平滑吸收”，无需根据位置差猜测事件来源。暂停、缓冲和结束状态不推进锚点。

房主每 5 秒上报本地位置、暂停标志和 `readyState`。该遥测只有同时满足以下条件才刷新锚点并产生新 revision：

- 房间处于 `playing`；
- 房主没有暂停且 `readyState >= 3`；
- 相对服务端时间线的偏差至少为 750ms；
- 连续两个样本的偏差方向相同；
- 距离上一次锚点刷新至少 15 秒。

播放、暂停、拖动、倍速变化和缓冲状态变化都会清空心跳候选样本。这样偶发慢请求不会形成“服务端修正房主 → 房主 seek → 再次缓冲”的反馈环。

## 时钟估计

客户端使用 NTP 四时间戳中点公式估计 `serverUnixMs - clientMonotonicMs`。最多保留 12 个样本，并从 RTT 最低的 5 个样本中取 offset 中位数。

首个有效样本直接建立 offset。后续样本：

- RTT 小于 0 或大于 5 秒时丢弃；
- offset 变化不超过 8ms 时视为噪声；
- 其余变化按 20% 平滑，每个样本最多移动 25ms。

因此重采样不会让成员的期望播放位置瞬间跳变。

## 成员漂移控制

成员每 750ms 比较本地位置与权威期望位置，漂移定义为：

```text
drift = actual - expected
```

控制器是有状态的，并使用进入/退出两个不同阈值：

| 条件 | 行为 |
|---|---|
| 尚未校准且偏差小于 420ms | 保持公共倍速，不校准 |
| 已在校准且偏差回到 220ms 内 | 退出校准并恢复公共倍速 |
| 偏差为 220–2400ms | 渐进调整倍速 |
| 偏差超过 2400ms，但未持续 1800ms | 只做渐进调整 |
| 同方向大偏差持续至少 1800ms | hard seek 到权威位置 |

成员落后时最多提速 5%，超前时最多减速 3%。变速幅度随偏差线性增加；不同的进入/退出阈值避免在边界上来回切换。

hard seek 后 3.5 秒内禁用漂移校准，并且两次 hard seek 至少间隔 12 秒。大偏差方向反转时，持续时间重新计算。软校准持续 2 秒后才在界面显示“正在平滑校准”，短暂校准对用户保持静默。

## 状态应用规则

客户端收到更高 revision 时总是更新逻辑状态，但不会无条件修改 `currentTime`：

- 房主仅在初次 snapshot、切换媒体或自己主动拖动时定位；心跳锚点永不定位房主。
- 成员仅在初次 snapshot、切换媒体、`timelineEpoch` 递增，或暂停态检测到至少 1 秒的离散跳变时立即定位。
- 播放中的普通心跳锚点只交给漂移控制器平滑吸收。
- 未来播放锚点到达前播放器保持暂停，避免在 350ms 调度窗口里提前播放。
- phase 或媒体切换后进入 3.5 秒稳定窗口，避免加载和播放启动事件被误判为漂移。

## 缓冲状态机

`waiting`/`stalled` 首先进入“疑似缓冲”，立即停止漂移校准但不改变 UI、不上报服务端。只有连续 1.8 秒仍满足 `readyState < 3` 才确认为本地缓冲。程序化 seek 产生的媒体事件另有 2.5 秒保护窗口。

确认缓冲后的行为：

- 成员：仅上报遥测，等待自己的数据恢复，不改变房间 phase。
- 房主：本地暂停并发送 `host_buffering`，服务端冻结权威锚点并广播 `buffering`。
- 其他成员：收到 `buffering` 后暂停，但不反复 seek。

播放器恢复到 `readyState >= 3` 后必须稳定 600ms。房主只有在服务端已经进入 `buffering` 后才发送 `host_ready`，服务端再生成带 350ms 未来锚点的 `playing` 状态，让所有人统一恢复。该顺序避免 `waiting/canplay` 快速交替制造 revision 风暴。
